# M1 WAN 탐침 — 운영 엔진(Vultr 서울) 인터넷 경유 영상·음성 도달 시험

> 작성 2026-10-31 · 단계 M1(PRD_01 5절 통과 기준 "발표자 1 → 청중 2 영상, 같은 LAN·LTE") · 코드 `media/tools/probe/`
> 목적 ① 엔진이 홈 PC → VPS(공인 IP)로 옮긴 뒤 **LAN 밖(인터넷) 경로**로 발표자 영상·음성이 청중에게 가는지 자동으로 잰다.
> 목적 ② 현장 버그(2026-10-31 마스터) "같은 Wi-Fi 두 사람은 서로 들리고, 외부 사용자 목소리는 우리가 듣는데 외부 사용자는 우리 소리를 못 듣는다" — **음성을 발행 중인 참가자가 남의 음성을 받는가**를 엔진 쪽에서 가린다.

## 1. 실행

```bash
cd sitemap/seminar.pi/media
go run ./tools/probe                       # 기본 = 운영 wss://158.247.243.145.sslip.io/signal, Origin https://seminarz.vercel.app, 측정 10초
go run ./tools/probe -url ws://127.0.0.1:7880/signal -dur 5s   # 로컬 엔진
go test ./tools/probe                      # 탐침 자체 점검(WS 프레이밍·env 파일 규칙, 루프백만)
```

| 옵션 | 기본 | 뜻 |
|---|---|---|
| `-url` | `wss://158.247.243.145.sslip.io/signal` | 시그널 주소(`ws://`·`wss://`) |
| `-origin` | `https://seminarz.vercel.app` | WS Origin(엔진 `MEDIA_ALLOWED_ORIGINS` 안의 값이어야 함) |
| `-dur` | `10s` | 측정 창 |
| `-warmup` | `15s` | 모든 기대 트랙의 첫 패킷 대기 상한 |
| `-env` | `../.env.local` | 비밀 키 파일(환경변수가 먼저) |

- 입장권은 탐침이 직접 서명한다(`signal.Sign`, HS256·aud `seminar-media`·60초·jti 무작위). 키 = 환경변수 `MEDIA_TOKEN_SECRET`(32자 이상) → 없으면 `-env` 파일의 같은 키 **마지막 줄**(dotenv 와 같은 규칙 — `.env.local` 에 두 줄이 있고 유효한 43자 줄이 뒤에 있다). 값은 어디에도 출력하지 않는다.
- 방 = 매 실행 새 무작위 `probe-<hex8>`. 끝나면 봇 3개가 `leave` → 엔진이 빈 방을 바로 정리하고, `MEDIA_ADMIN_SECRET` 이 있으면 `GET /admin/rooms` 로 방이 없어졌는지 확인(남았으면 `DELETE`).
  - 마지막 줄 읽는 법 : `방 정리 확인 : … 없음(엔진 방 N개)` = 관리 API 가 **200 + JSON 배열**로 답했고 그 안에 탐침 방이 없음. `관리 API 응답 401 — 방 정리 확인 불가`처럼 "확인 불가"면 키 틀림·관리 API 꺼짐(404) 등으로 **확인하지 못한 것**이다(2026-10-31 리뷰 수정 전에는 이 경우도 "없음(엔진 방 0개)"로 찍혔다).
  - 평문 `ws://` 이면서 루프백이 아닌 주소에는 관리 키를 보내지 않는다(확인 생략). 기본값(운영)으로 돌면 첫 줄에 `※ 운영 엔진 대상(기본값)` 을 찍는다.
- 종료 코드 0 = PASS, 1 = FAIL, 2 = 키 없음(방 정리 확인 결과는 종료 코드에 넣지 않는다 — 출력 마지막 줄로 본다).
- 위치가 `cmd/`·`internal/` 이 아닌 이유 : `internal/archtest` 가 두 디렉터리 아래 패키지를 OWNERSHIP 구조도와 대조하므로 새 패키지가 들어가면 관문이 깨진다. 새 외부 의존성 없음(pion + 표준 라이브러리, wss 클라이언트는 `signal.DialWS` 가 `ws://` 만이라 최소 구현을 따로 둠).

## 2. 시나리오와 판정

| 순서 | 봇 | 동작 |
|---|---|---|
| 1 | P (presenter) | 입장 → 발행 PC 에 VP8 영상(33ms, 1000B, 30프레임마다 키프레임) + Opus 음성(20ms, 80B) → `produce` 2건 |
| 2 | A1·A2 (audience) | 늦은 합류자로 입장(자동 구독) |
| 3 | P → A2 | `peer.setRole panel`(무대 승격) |
| 4 | A2 (panel) | 발행 PC 에 Opus 음성 → `produce`(mic) — **현장 버그 재현 지점 : 발행 중인 A2 가 P 음성을 계속 받는가** |

기대 수신 행렬 : A1 ← P 영상·P 음성·A2 음성 / A2 ← P 영상·P 음성 / P ← A2 음성(자기 것은 받지 않음).
판정 : 모든 트랙 첫 패킷(또는 warmup 상한) 뒤 측정 창에서 **받은 수 ÷ 보낸 수 ≥ 80%** 면 PASS. 수신 봇은 pion 기본 API(NACK·RR 인터셉터) — 브라우저처럼 RTCP 를 보낸다.
받은 수는 **RTP 순번 기준 고유 패킷 수**다(NACK 재전송으로 같은 순번이 다시 와도 한 번만 셈 — 손실 망(LTE·netem)에서 비율이 부풀어 손실을 가리지 않게, 실행 4부터 적용). 순번이 반 바퀴(32768) 지나면 다시 세므로 측정 창이 길어도 맞다.

- 영상 303/304·음성 499/500 의 1개 차이는 창 끝에 날아가던 패킷(손실 아님 — 같은 실행의 다른 경로·다른 실행은 100%).
- 실행 4 는 순번 중복 제거를 켠 뒤다. 같은 망에서 중복을 빼도 같은 수준이므로 실행 1~3 의 100% 가 재전송 중복으로 부풀었을 가능성은 낮다(직접 증명은 아님).
- ICE 선택 쌍 : 5개 PC 모두 `host → host 158.247.243.145:7882 (udp)` — 집 공유기 NAT 를 넘어 VPS 공인 IP 의 UDP mux 로 직접 연결(엔진은 들어온 점검으로 peer-reflexive 후보를 학습). PC 연결 완료 = 시작 후 1.1~4.3초, 첫 패킷 = 송출 시작 후 1.0~2.0초.
- 엔진 `join` 응답 `iceServers` = 0개(VPS `MEDIA_ICE_SERVERS` 미설정). 브라우저는 여기에 `/api/media/turn` 의 TURN 을 더해 쓴다.
- 방 정리 : 실행 1~3 도 "없음(엔진 방 0개)"를 찍었으나, 당시 코드는 관리 API 응답 코드·JSON 해석 오류를 보지 않아 401·404 도 같은 문구가 나왔다 → **실행 1~3 의 정리 확인은 증거가 아니다**. 실행 4(수정 뒤)는 200 + JSON 배열로 `probe-f9b9ac3e 없음(엔진 방 0개)` — 실제 확인이고, 같은 키·같은 엔진이라 관리 키가 유효함도 보여 준다. 엔진은 마지막 `leave` 때 자동 생성 방을 바로 치우므로(bora `manager.go` reap) 실행 1~3 의 방이 남았을 가능성은 낮고, 실행 4 시점 엔진 방 0개라 남은 방은 없다.
- 참고(로컬 엔진, 같은 PC) : 14회 중 13회 PASS. 첫 1회는 A2 발행 PC 가 연결되지 않아 A2 음성 0 — 이후 13회 재현 안 됨(새 실행 파일의 첫 UDP 바인딩·가상 어댑터 후보가 겹친 것으로 추정, 원인 미확정). WAN 3회에는 없었다.

## 4. 결론 — 현장 버그

**사실 : VPS 엔진은 WAN 에서 "음성을 발행 중인 참가자"에게 발표자 음성을 99~100% 전달한다**(A2←P 음성, 반대 방향 P←A2 도, 4회). 같은 방에서 발행·구독 PC 를 동시에 쓰는 참가자, 승격 뒤 발행, 늦은 합류자의 재협상(새 m-line 추가)까지 모두 정상이다. 관리 API 에 producer 가 보였다는 현장 확인과도 맞는다.

**유력 추정(실기기 재시험 전 미확정) : 원인은 클라이언트 재생 쪽.** 근거는 집 NAT → VPS 로 붙는 pion 봇의 소거법 + 증상 일치뿐이다. 같은 날 커밋 `9396d9a1`(`src/components/room/stage.tsx` `useRemoteAudio`)이 이 증상 — 무대에서 마이크를 켜는 순간(getUserMedia) 휴대폰 WebView 가 오디오 세션을 바꾸며 재생 중인 `<audio>` 를 멈추고, 스트림이 그대로라 다시 재생되지 않던 문제 — 를 `pause` 감지 → 재생 재시도로 고쳤다. 외부 사용자가 휴대폰으로 무대에 올라 마이크를 켠 경우와 맞는다(같은 Wi-Fi 두 사람이 PC 였다면 증상이 없던 것도 설명됨).

이 추정을 가르는 질문 [확인중 : 마스터] :
1. **현장 세션이 열린 엔진 = VPS 인가, 이전 집 PC 엔진(cloudflared + UDP 포트포워드)인가?** VPS 이전 문서 `da690f26` 은 09:11, 수정 `9396d9a1` 은 09:38 커밋이다. 집 PC 엔진이었다면 이 탐침(VPS 대상)은 그 세션의 엔진을 시험한 것이 아니다.
2. **외부 사용자에게 발표자 영상은 보였는가?** 보였다면 구독 PC(발행 PC 와 다른 ICE 세션)가 살아 있었다는 뜻 → 전송 경로가 아니라 재생 문제 쪽으로 기운다. 영상도 안 보였다면 구독 PC 연결(NAT·ICE) 실패 쪽을 다시 봐야 한다.
3. 외부 사용자의 기기(휴대폰·PC)·브라우저(Pi Browser 여부)·역할(무대 승격 여부).

엔진 수정 필요 : 현재 증거로는 없음(M3 전달 사항 현재 없음 — 위 1·2 답에 따라 다시 본다).

탐침이 브라우저와 다른 점(결론의 한계) : 실제 코덱·`<audio>` 재생 없음, mDNS 후보 없음, TURN 미사용, 이 PC 의 집 NAT ≠ 이동통신 CGNAT.

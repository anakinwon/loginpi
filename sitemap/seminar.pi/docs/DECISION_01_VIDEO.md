## 1. 질문

seminar.pi 핵심 기능인 화상 세미나를 어떻게 만들까?

1. 이미 있는 **무료 화상채팅 기능**을 활용해 서비스한다.
2. **REA로 기존 화상채팅 프로그램을 분석**해서 웹·앱 기능을 새로 만든다.

| 기준 | ① 기존 무료 화상채팅 활용 | ② REA로 분석 후 새로 제작 |
|---|---|---|
| 법적 위험 | 오픈소스 SDK를 쓰면 라이선스 조건만 지키면 된다. 공개 서비스에 끼워 넣으면 이용조건 위반 위험이 있다(F5) | **위험 큼**. 상용 프로그램은 이용약관(EULA)에서 역분석을 제한하는 경우가 많다. 국내 저작권법 제101조의4는 호환에 필요한 정보 획득 범위에서만 프로그램코드역분석을 허용하는 취지다. 분석 결과를 경쟁 제품 개발에 쓰면 침해 소지가 크다. 법률 판단은 [확인중 : 법무] |
| 해결하는 문제 | 영상 중계 서버(SFU)·네트워크 우회(TURN)·화질 자동 조절을 그대로 받는다 | 화면(UI)은 이해할 수 있지만 **진짜 어려운 부분인 중계 서버·운영**은 분석으로 얻을 수 없다 |

## 4. 권고 — ①의 변형 "오픈소스 화상 엔진 + 우리 화면"

**공개 무료 서비스에 끼워 넣지 않고, 오픈소스 화상 엔진(SFU)을 SDK로 붙인 뒤 화면과 결제는 seminar.pi가 직접 만든다.** ②(REA로 역분석)는 채택하지 않는다.

| 층 | 선택 | 이유 |
|---|---|---|
| 영상 중계 | **LiveKit**(오픈소스 SFU) — 시작은 LiveKit Cloud 무료, 규모가 커지면 자체 호스팅이나 유료로 전환 | 1명이 다수에게 보내는 구조에 맞다. PRD_9가 오디오 SFU 확장 여지로 이미 언급한 후보다(F2) |
| 대안 후보 | Cloudflare Realtime SFU | cafe.pi가 Cloudflare TURN을 1순위로 쓰도록 바꿨다(F1-2). S0에서 비교한다 |
| 네트워크 우회 | cafe.pi `turn-credentials` 방식 재사용 | Pi Browser에서 통한 자산이다(F1) |
| 입장 통제 | 우리 서버가 **Pi 결제 확인 뒤** 화상 방 입장 토큰을 발급(짧은 유효기간) | 유료 세미나(R1) 성립 조건. 서버 금액 재검증 원칙과 같다 |
| 화면 | seminar.pi 자체 UI(목록·상세·방·개최) | 등재 독립 완성도와 브랜드 |

**PRD_27 전제(F7)와 다른 점과 사유**: PRD_27은 PyVoice™ 메시 확장을 전제로 했다. 하지만 메시 방식은 다수 시청 구조에서 성립하지 않으므로(F3) SFU를 택한다. **TURN 재사용이라는 전제는 그대로 지킨다.** 이 변경은 마스터 승인 시 PRD_27 해당 행에도 반영한다.

**공개 무료 서비스 끼워 넣기(① 원형)를 피하는 이유**: 끼워 넣기가 막혀 있고(F5), 결제한 사람만 들어오게 막을 수 없으며, Pi Browser에서 외부 사이트로 나가면 로그인이 끊기고 등재 심사에서 자체 기능 없음으로 보일 위험이 있다.

## 7. 마스터 결정 (2026-10-24) — ② 자체 구축, 엔진까지 처음부터

**결정**: 화상 기능을 자체 구축한다. 영상 중계 엔진(SFU)까지 직접 작성한다.

**이유(마스터)**:
1. 도전정신
2. 기존 제품을 쓰면 로고가 붙는 문제
3. 요금제·사용기간 부담

서비스(아소카)는 1~6절 권고와 다르지만 이 결정을 따른다. 다만 아래 7.1의 안전 원칙 2개는 **서비스가 제안한 범위 축소**다(S-1 = 연결·암호 계층은 직접 작성하지 않음, S-2 = 상용 프로그램 디컴파일 안 함). 마스터 동의 전까지 [확인중 : 마스터].

### 7.1 안전 원칙 (서비스 제안 — 마스터 동의 대기)

| 원칙 | 내용 | 이유 |
|---|---|---|
| **S-1 연결·암호 계층은 직접 만들지 않는다** | 연결·보안 계층(ICE 연결 수립·DTLS·SRTP 암호화)과 RTP 패킷 직렬화는 표준을 구현한 검증된 프로토콜 라이브러리를 쓴다. **그 위의 중계 엔진 로직은 전부 직접 작성**한다: 방·발행/구독 관리, 패킷 전달, 손실 복구(NACK)·화면 재요청(PLI), 대역폭 추정, 화질 단계(simulcast) 전환, 녹화 | 암호 계층을 직접 짜면 보안 결함이 곧 사고다(업계 철칙). 이 라이브러리는 UI·로고·요금제가 없는 통신 부품이라 결정 이유 2·3에 걸리지 않는다 |
| **S-2 REA는 합법 범위에서만** | 분석 대상은 ① 공개 표준 문서(RFC·W3C WebRTC) ② 오픈소스 SFU 소스 읽기(REA 불필요) ③ **우리 세션의 동작 관찰**(브라우저 `chrome://webrtc-internals`·패킷 캡처)로 한정한다. **상용 화상 프로그램의 디컴파일·코드 이식은 하지 않는다**. 오픈소스는 읽고 설계를 배우되 코드는 옮기지 않는다 — 부득이 옮기면 해당 라이선스(Apache-2.0 등) 고지 의무를 지킨다 | 저작권법 제101조의4는 호환에 필요한 범위의 역분석만 허용하는 취지이고, 상용 이용약관은 역분석을 제한하는 경우가 많다. 법률 판단은 [확인중 : 법무] |

### 7.2 구조(초안)

```
[Pi Browser · 일반 브라우저]  seminar.pi 화면(Next.js, Vercel)
        │ ① HTTPS : 로그인·세미나·Pi 결제 확인 → 입장권(짧은 유효기간 서명 토큰) 발급
        │ ② WSS   : 시그널링(입장권 제시 → 방 참가·발행·구독 협상)
        │ ③ UDP/TCP(DTLS-SRTP) : 영상·음성
        ▼
[seminar 미디어 서버 — 자체 작성]  ← Vercel 에서 못 돌림(장시간 실행·UDP 필요) → 별도 VM
  ├ 시그널링(WebSocket) : 입장권 검증·방 상태
  ├ SFU 엔진 : 발행자 1 → 구독자 N 패킷 전달, NACK/PLI, 대역폭 추정, simulcast 전환
  ├ 프로토콜 스택(S-1 — 검증 라이브러리)
  └ 녹화(Phase 4, VOD R3)
[TURN] cafe.pi turn-credentials 방식 재사용(방화벽 우회)
```

| 결정 대기 항목 | 후보 | 서비스 의견 |
|---|---|---|
| 미디어 서버 언어 | **Go + pion**(WebRTC 프로토콜 스택 — SFU 아님, 엔진은 직접) / Node + werift(TypeScript 순수 구현) | Go + pion. 저지연·동시성에 유리하고, 대형 오픈소스 SFU들이 같은 스택을 쓴다. **pion은 ICE·DTLS·SRTP·RTP 직렬화만 쓰고, 기본 제공 인터셉터(NACK·TWCC·GCC 대역폭 추정)는 등록하지 않는다** — 손실 복구·대역폭 추정은 직접 작성(엔진 직접 원칙). 저장소에 Go가 처음 들어온다 [확인중 : 마스터] |
| 서버 호스팅 | 무료 등급 VM(예 : Oracle Cloud Always Free — 조건 [확인중 : 공식 페이지]) / 저가 VPS(서울 리전 지연 유리) | 시험은 무료 VM, 운영은 서울·도쿄 리전 VPS [확인중 : 마스터] |
| 코드 위치 | `sitemap/seminar.pi/media/`(같은 사이트 폴더, Next 빌드 제외) | 사이트 단위 분리 원칙(PDB)과 맞다 |

### 7.3 단계 계획 — 단계마다 통과 기준(go/no-go)

| 단계 | 만드는 것 | 통과 기준 |
|---|---|---|
| **S0 실기기 관문** | Pi Browser 카메라·마이크 `getUserMedia` + 브라우저 2개 직접 영상 연결(서버 없이) | iOS·Android Pi Browser에서 영상 송수신·자동재생 OK. **실패하면 전체 재검토** |
| S1 최소 SFU | 시그널링 + 발행자 1 → 구독자 2 패킷 전달(손실 복구 없음) | 같은 네트워크·LTE에서 영상이 보인다 |
| S2 안정화 | NACK(손실 재전송)·PLI(화면 재요청)·TURN 경유 | 손실 3% 환경에서 화면 깨짐이 회복된다 |
| S3 규모 | 대역폭 추정·simulcast 화질 전환·구독자 30명 | 30명 동시 시청, 개최자 업로드 1회선 유지 |
| S4 서비스화 | 입장권(Pi 결제 확인)·방 관리·관측(schema.pi 모니터링 연결)·녹화(VOD) | PRD F-04·F-05·F-07 충족, R-P0~P6 원장 통과 |

- 각 단계 끝에 TROUBLESHOOT 기록 + 원장 점검을 한다. 단계를 건너뛰지 않는다.
- 위험: 품질(화질·지연)이 상용 수준에 못 미칠 수 있다. 서버 운영(장애·보안 패치) 책임이 생긴다. 일정은 S0 통과 후 단계별로 산정한다 [TBD].

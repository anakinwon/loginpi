1. 요약

dbms.pi
CDC 방향 검토
요약

Kafka는 빼고 시작한다. 변경을 옮기는 일은 DB 로그와 오프셋 저장이 맡고, AI는 매핑·검증·감시를 맡는다

0 / 7
PRD CDC 요구사항(R00~R06) 중 Kafka가 있어야 하는 항목
1 / 5
CDC가 하는 일 5가지 중 Kafka가 꼭 필요한 일(팬아웃·재생)
7곳
Kafka 없는 로그 캡처를 기본 기능으로 적은 공식 문서

확인된 사실

  • 현재 PRD v0.7의 캡처 방식은 폴링(1차)과 PostgreSQL 논리 복제(2차)다. Kafka 항목은 없다
  • Debezium 공식 문서는 엔진(앱 내장)과 서버(싱크 20여 종) 모두 Kafka 없이 쓰는 방법을 안내한다
  • Claude API 공식 문서는 temperature 0.0에서도 결과가 완전히 결정적이지 않다고 적는다
  • AWS·Google의 이행 서비스는 규칙 엔진이 먼저 변환하고, 남은 부분을 생성형 AI가 돕는다

판단

  • 권장고객망 워커(Java)에 Debezium 엔진을 넣고, 오프셋은 대상 DB에 둔다
  • 권장AI는 매핑 초안·검증 SQL·스키마 변경 영향·지연 이상 설명을 맡는다. 결과는 사람 승인과 결정적 검증을 거친다
  • 조건부재검토 신호 5개 중 2개가 생기면 Kafka를 전송 구간에 넣는다
  • 배제AI가 주기적으로 차이를 조회해 변경을 만드는 방식
시사점 : 핵심 장치는 변경을 빠짐없이 순서대로 옮기는 부분이다. 이 일은 DB 로그와 오프셋 저장이 맡고, Kafka와 AI는 그 앞뒤를 돕는다.

질문과 답

로그 캡처는 Kafka 없이 된다. AI는 Kafka 자리를 맡지 못한다. 검증된 제품은 각 클라우드 안에 있다

질문답공식 문서 근거조건·한계
① DB 로그 기반 캡처를 Kafka 없이 할 수 있나?된다PostgreSQL 논리 디코딩·복제 슬롯, Oracle LogMiner, Debezium 엔진·서버("Kafka 없이 원천에서 바로"), Supabase·Google·Databricks 관리형 CDC최소 1회 전달이라 멱등 적재, 읽은 위치 기록, 슬롯 감시가 필요하다
② AI가 Kafka 역할을 대신할 수 있나?못한다Kafka는 내구성·파티션 순서·보존 기간 재생을 보장한다. Claude API는 상태를 저장하지 않고, temperature 0.0에서도 결과가 완전히 결정적이지 않다AI는 Kafka·CDC를 받아 쓰는 쪽이다(Confluent Streaming Agents, Debezium AI)
③ Kafka 없는 Debezium과 AI로 대신할 수 있나?조건부로 된다Debezium 엔진 문서 : 장애 대응을 Kafka Connect 대신 앱이 맡는다. Debezium AI : 임베딩 변환(Java 21 이상), PyDebeziumAI(Kafka 없이 프로세스 안에서 실행)재시작·오프셋은 워커가 맡는다. Debezium AI는 AI용 데이터 준비 기능이라, 매핑·검증 AI는 따로 만든다
④ 같은 기능을 갖춘 검증된 솔루션이 있나?클라우드 안에는 있다Supabase Pipelines(공개 알파)와 자동 임베딩, AWS DMS와 생성형 AI 변환, Google DMS·Datastream과 Gemini, Snowflake Openflow와 Cortex, Databricks Lakeflow Connect대상이 그 회사 클라우드여야 한다. 고객 온프레미스 Oracle·Tibero에서 고객이 정한 대상으로 가는 범용 제품은 찾지 못했다
시사점 : AWS·Google 공식 문서는 "규칙 엔진이 먼저 변환하고, 남은 부분을 생성형 AI가 돕는" 구조를 쓴다. dbms.pi도 같은 원칙을 따른다.

5. 질문 ① 로그 캡처는 Kafka 없이 되는가

dbms.pi
CDC 방향 검토
공식 문서 ①

PostgreSQL·Oracle·Debezium·관리형 서비스 공식 문서 모두 Kafka 없는 로그 캡처를 기본 기능으로 적고 있다

공식 문서문서 내용dbms.pi에 주는 조건
PostgreSQL 18 문서 47.2 논리 디코딩WAL을 해석해 테이블 변경을 꺼낸다. 복제 슬롯은 변경을 원래 순서대로 재생하고, 연결과 상관없이 남으며 크래시에도 유지된다원천 PG는 Kafka 없이 바로 읽는다
같은 문서크래시 뒤 슬롯이 이전 LSN으로 돌아가 최근 변경을 다시 보낼 수 있다. 중복 처리는 클라이언트가 맡는다마지막 LSN 기록, 멱등 upsert
같은 문서(주의)슬롯은 소비자가 없어도 WAL을 붙잡는다. 심하면 DB가 멈출 수 있으니 필요 없는 슬롯은 지운다슬롯 경보·정리(CDC-R06)
Oracle DBMS_LOGMNRLogMiner는 온라인·아카이브 redo 로그를 SQL(V$LOGMNR_CONTENTS)로 조회한다Oracle 원천도 Kafka 없이 읽는다(보충 로깅·권한 필요)
Debezium 엔진 문서Kafka 브로커와 Connect 없이 커넥터를 앱 안에 넣어 변경 이벤트를 직접 받는 방법을 안내한다Java 워커에 내장한다
Debezium 서버 문서"Kafka 없이 원천에서 메시징·저장 시스템으로 바로" 보낸다. 싱크 20여 종(JDBC·Iceberg·Pub/Sub·Kinesis·Redis·NATS 등)별도 프로세스로도 쓸 수 있다
Supabase·Google·Databricks 문서Supabase Pipelines, Datastream, Lakeflow Connect 모두 로그 기반 CDC를 Kafka 없이 제공한다. 전달은 최소 1회, Datastream은 순서를 보장하지 않는다관리형 선택지
정리 : 공식 문서 7곳이 Kafka 없이 로그를 읽는다. 공통 조건은 중복 처리(멱등), 읽은 위치 기록, 슬롯 감시 세 가지다.
※ 출처 : 참고 자료 (1/2) 1~4, 11, 16, 18

6. 질문 ② Kafka가 보장하는 것과 LLM이 보장하지 않는 것

dbms.pi
CDC 방향 검토
공식 문서 ②

Kafka는 잃지 않고, 순서대로, 다시 읽게 하는 저장 계층이다. LLM 공식 문서는 같은 입력에도 다른 출력을 인정한다

Kafka 공식 문서(Design, 4.3)

  • 내구성 : 커밋된 메시지는 동기화된 복제본이 하나라도 살아 있으면 잃지 않는다
  • 순서 : 한 파티션 안에서 전체 순서를 지킨다
  • 보존·재생 : 토픽마다 보존 기간을 정하고, 소비자는 그 안에서 원하는 위치부터 다시 읽는다
  • 전달 : 기본은 최소 1회. 멱등 프로듀서와 트랜잭션으로 Kafka 안에서는 정확히 1회. 외부 시스템까지는 그 시스템의 협조가 필요하다

Claude API 공식 문서

  • temperature 0.0에서도 결과가 완전히 결정적이지 않다
  • 같은 입력이 호출마다 다른 출력을 낼 수 있다(용어집)
  • Messages API는 상태를 저장하지 않는다. 대화 이력은 매 호출마다 앱이 보낸다. 서버 보관 기능(베타)도 마지막 요청 뒤 5분이면 만료되고, 기준 사본은 앱이 지킨다
  • 메시지 보존, 순서 보장, 재생 위치 같은 기능은 문서에 없다

업계 공식 구조 : AI는 Kafka·CDC 뒤에서 일한다

  • Confluent 문서 : Streaming Agents는 Flink 위에서 데이터 스트림 안에 AI 에이전트를 돌리고, Real-Time Context Engine이 Kafka 토픽 데이터를 MCP로 외부 에이전트에 넘긴다
  • Debezium 문서 : 임베딩 변환·PyDebeziumAI로 변경 이벤트를 AI용 데이터로 바꾼다
정리 : Kafka가 맡는 일은 저장·순서·재생이다. LLM 공식 문서는 이 성질을 보장하지 않고, Confluent·Debezium 문서는 AI를 Kafka·CDC 뒤쪽 소비자로 둔다.
※ 출처 : 참고 자료 (1/2) 7~10, 5~6

7. 질문 ③ Kafka 없는 Debezium과 Debezium AI 기능

dbms.pi
CDC 방향 검토
공식 문서 ③

Debezium은 Kafka 없이 돌고, AI 기능도 공식으로 붙어 있다. Kafka Connect가 하던 장애 대응은 워커가 맡는다

구성공식 문서 내용상태dbms.pi 적용
Debezium 엔진(Java 라이브러리)앱 안에 커넥터를 넣는다. 3.2부터 비동기 엔진이 기본. 오프셋 저장소는 파일·DB 등에서 고른다정식SchemaPiAgent에 내장, 오프셋은 대상 DB
장애 대응 차이Kafka Connect는 분산 서비스라 한 노드가 죽으면 다른 노드가 커넥터를 다시 띄운다. 모든 앱에 이 수준이 필요하진 않고, 엔진 방식은 앱이 직접 갖춘다문서 설명워커 재시작·하트비트(Phase 5 프로토콜)
Debezium 서버Kafka 없이 싱크로 바로 보낸다. JDBC 싱크(upsert), Iceberg 싱크 포함정식고객망 별도 프로세스 대안
임베딩 변환(FieldToEmbedding)변경 이벤트의 텍스트 칼럼을 임베딩 벡터로 바꿔 붙인다. 공급자 Hugging Face·Ollama·ONNX MiniLM·OpenAI·Voyage AI. Java 21 이상 필요Red Hat 빌드 기준 개발자 미리보기레이크 curated층 의미 검색용(선택)
PyDebeziumAIPython 프로세스 안에서 엔진을 돌려 Kafka 없이 벡터 DB(Chroma·PGVector·Milvus)에 반영한다. 기본 키 기반 멱등 ID공식 패키지(2026-10 발표)워커가 Java라 해당 없음
AI 관련 싱크Milvus·Qdrant(벡터 DB), InstructLab정식필요할 때
정리 : Debezium 공식 AI 기능은 변경 데이터를 AI가 쓰기 좋게 바꾸는 쪽이다. 매핑 규칙 작성·검증 같은 이행 AI는 Debezium 범위 밖이다.
※ 출처 : 참고 자료 (1/2) 3~6 · Debezium 3.x는 Java 17 이상, 임베딩 변환은 Java 21 이상

12. Kafka가 다시 필요해지는 신호

dbms.pi
CDC 방향 검토
재검토 조건

아래 신호 가운데 2개 이상이 생기면 Kafka 도입을 다시 검토한다

신호그때 Kafka가 유리해지는 이유지금 상태
① 같은 변경을 3곳 이상이 받는다(레이크·검색·캐시·알림 등)원천 슬롯 하나로 여러 소비자를 각자 속도로 받는다2곳(대상 DB·레이크)
② 대상 장애가 길어 원천 WAL이 쌓일 위험이 크다Kafka가 중간 버퍼가 되어 원천 디스크를 지킨다슬롯 경보·정리 절차(CDC-R06)로 관리
③ 고객사가 이미 Kafka를 표준으로 운영한다그 Kafka에 이벤트를 넣으면 된다. 운영은 고객사가 맡는다해당 고객 없음
④ 며칠 전 변경까지 다시 돌려야 한다(재처리·재생)토픽 보존 기간 안에서 원하는 시점부터 재생이행 리허설은 스냅샷과 재시작으로 대응
⑤ 초당 수만 건 이상, 원천 여러 개가 합류한다파티션으로 나눠 병렬 처리1차 원천 1개

지금 할 대비

  • 변경 이벤트는 Debezium 변경 이벤트 형식(before·after·op·source)으로 맞춘다. 나중에 Kafka를 넣어도 바뀌는 곳은 전송 구간 하나다
  • 오프셋과 처리 이력은 대상 DB 테이블에 남긴다. Kafka로 옮길 때 시작 지점을 그대로 넘길 수 있다
Key Finding : Kafka를 빼는 결정은 되돌릴 수 있다. 이벤트 형식과 오프셋 기록을 지키면 나중에 넣는 비용이 작다.

13. 판단과 단계별 계획

dbms.pi
CDC 방향 검토
판단

dbms.pi 7단계는 Kafka 없이 시작하고, AI는 규칙 엔진 다음 자리에서 매핑·검증·설명을 맡는다

단계별 계획

단계내용
1. PoCpitel-pg 한 주제영역에서 워커(Debezium 엔진, pgoutput)로 읽어 대상 PG에 JDBC upsert, 레이크 raw층에 Parquet로 쓴다. 오프셋은 대상 DB 테이블
2. 폴링 병행로그 권한이 없는 원천은 폴링 어댑터(CDC-R00~R02) 유지, 스키마 변경 영향 연동(CDC-R05)
3. 원천 확장Oracle은 Debezium LogMiner, Tibero는 ProSync 연계나 폴링 중 선택(PRD 10절 #8)
4. 재검토재검토 신호 2개 이상이면 Kafka(또는 호환 브로커)를 전송 구간에 넣는다

AI가 맡는 일 (규칙 엔진 다음, 사람 승인과 결정적 검증을 거침)

  • PiMig 매핑·변환 규칙 : 표준용어 규칙으로 먼저 매핑하고, 남은 칼럼을 AI가 초안으로 채운 뒤 MIG·DA 승인
  • 검증 SQL(건수·합계·샘플 대조) 생성, 판정은 실행 결과로
  • 스키마 변경이 닿는 파이프라인 설명
  • 지연(lag)·오류 급증의 원인 설명과 조치 제안
  • 선택 : curated층 텍스트 칼럼 임베딩(Debezium 임베딩 변환, Java 21)
  • 맡기지 않는 일 : 변경 읽기, 오프셋 관리, 적재 성공 판정
판단 : 전송 구간에서 Kafka를 빼고, 변경 이벤트 형식과 오프셋 기록으로 나중의 선택지를 열어 둔다. AI 사용 순서는 AWS·Google 공식 문서와 같게 규칙 먼저, AI 다음이다.
